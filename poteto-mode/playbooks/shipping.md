### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge, then verify each PR independently before it lands.** Use the active host's forge tool or an available CLI for the repository. An independent verifier per PR runs the change as a user would on the real surface, parent against head, and records `PASS`, `PASS+NOTES`, or `FAIL` with evidence. CI and bot approval are not substitutes. If no independent verifier or real-surface driver is available, perform the available checks sequentially, report the missing independence or access, and stop before merging.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Use the available forge to merge the lowest unmerged PR, subject to approval and permissions. Check forge-specific stack semantics: on GitHub, a PR based on its parent's branch merges into that branch, not trunk; Origin's plain merge may include lower PRs. Read back the state and base to distinguish a landed merge from a queue or auto-merge request. Enable auto-merge only for a verdict covering the current head. After a merge lands, retarget the next PR to trunk and move its patch onto the merge result when authorised; use a lease for any permitted force-push. Apply step 3's patch-id rule, then wait for checks and a surviving verdict before merging it.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base. On GitHub, the shipped `scripts/watch-pr/watch-pr --queued-stack` can watch the run with Bun and authenticated `gh` access. It bootstraps dependencies with `bun install --frozen-lockfile` if needed; run it only when that installation is permitted. Pass PR numbers bottom-to-top via `--stack-prs` and preserve that list on restart. Otherwise use the forge's status and checks views to recheck each PR until the ceiling is merged. A scheduler may repeat these checks if the host supports it; otherwise monitor during the session and report that unattended monitoring is unavailable. A base moving to trunk when its parent merges is expected. Investigate stalls before changing anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
